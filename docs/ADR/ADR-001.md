# ADR-001: RADAR Canonical Knowledge Model

**Status**: Accepted  
**Date**: 2026-07-14

## Context
RADAR initially stored scraped job opportunities as denormalized, point-in-time JSON files (`live-scraped.json`). This created significant data duplication, hindered referential integrity, and made temporal intelligence (e.g., tracking how a job posting changes over time) impossible. 

As we pivot to a Decision Intelligence platform, we require a canonical, immutable knowledge graph.

## Decision
We adopt a normalized Entity-Relationship model stored in SQLite. The architecture mandates the following invariants:

1. **Identity & Idempotency**: All entities use deterministic identity. Re-scraping the same role multiple times must resolve to the same `Opportunity`, while tracking changes in immutable `Documents`.
2. **Provenance**: Every derived entity (`Fact`, `Claim`, `Assessment`, `Recommendation`) must maintain a strict, unbreakable lineage back to the raw `Evidence` (and its `Document` / `Source`).
3. **Immutability of Observation**: Acquisition ends at `Facts`. `Facts` are objective and immutable. 
4. **Mutability of Interpretation**: `Claims`, `Assessments`, and `Recommendations` are interpretations. They are versioned and tied to specific Prompt/Model combinations. If intelligence improves, we re-assess, but we never re-scrape.

### Core Schema
- **Acquisition Domain**: `Source` -> `Document` -> `Evidence` -> `Fact`
- **Intelligence Domain**: `Fact` -> `Claim` -> `Assessment` -> `Recommendation`

## Consequences
- The web scraper is stripped of its persistence responsibilities. It now only outputs raw observations (`DetailedCard`, `ExtractionResult`) which are mapped by a pure `KnowledgeGraphBuilder`.
- All future features (Decision Memory, Company Signals) will build exclusively on this graph.
- Requires rigorous certification gates to ensure schema drift or LLM hallucination doesn't break the graph's integrity.
