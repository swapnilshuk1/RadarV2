# ADR-002: Event Sourcing & CQRS

**Status**: Accepted  
**Date**: 2026-07-15

## Context
As RADAR transitions from a static recommendation engine into a longitudinal executive decision-support system, modeling decisions and outcomes as mutable state (e.g., `UPDATE decisions SET action = 'Pursue'`) destroys critical historical context. 
If an executive passes on an opportunity in January but accepts a similar one in March, the system must remember *why* their thinking changed and *what* they saw when making the decision. Furthermore, as the system grows to ingest complex signals (layoffs, compensation changes, recruiter emails), a unified chronological history becomes essential.

## Decision
We adopt **Event Sourcing** for all executive journey events and **CQRS (Command Query Responsibility Segregation)** for all user-facing views.

### 1. The Single Career Journey Timeline
Instead of fragmented `decision_events` and `outcome_events` tables, all events are appended to a unified, chronologically sorted `TimelineEvent` stream. 
- **Hybrid Schema**: Common fields (`aggregateId`, `eventType`, `occurredAt`) are relational columns for fast filtering, while event-specific payloads are stored in JSON.
- **Event Taxonomy**: Events are strictly classified by `EventCategory` (`Acquisition`, `Graph`, `Recommendation`, `Decision`, `Outcome`, `Signal`, `Memory`, `System`, `External`) and are explicitly versioned (`eventVersion`) to ensure backward compatibility during replays.
- **Ordered IDs**: We use UUIDv7 (or ULID) for primary keys to guarantee distributed chronological sorting without relying solely on timestamps.

### 2. Immutable Snapshots
A `RecommendationSnapshot` is created and frozen the moment a user views or acts upon an opportunity. 
The Timeline Event holds a reference to this `snapshotId`. If the underlying Knowledge Graph updates tomorrow, the snapshot remains untouched, guaranteeing we can perfectly replay what the executive saw on that day.

### 3. First-Class Predictions
Predictions (Expected Probability, Expected Salary, Expected Funnel) are treated as versioned, first-class objects linked to Assessments. This decouples the act of predicting from the act of calibrating, allowing us to defer calibration until we reach statistical significance (100+ recorded outcomes).

### 4. Disposable Projections (CQRS)
The Timeline is the single source of truth. User interfaces (like the Executive Daily Brief or the Decision Queue) do not query the event store directly. Instead, they query **Projections** (Read Models).
- Projections contain no business logic.
- Projections can be entirely destroyed and rebuilt at any time (`npm run rebuild-projections`) by replaying the Timeline.

## Consequences
- **Replayability**: We gain the ability to time-travel the platform to any given day.
- **Signal Engine**: The architecture naturally supports a proactive `SignalEngine` emitting `RecommendationChanged` or `CompanyLayoffs` events into the timeline.
- **Certification Overhead**: Our CI pipeline must now certify *Projection Consistency*—ensuring that a projection rebuilt from scratch exactly matches a projection maintained incrementally.
