# ADR-004: Decoupling Functional Role Classification from Evidence Richness in RADAR

**Status**: Accepted  
**Date**: 2026-07-18  

## Context

The LLM-based role classification experiments in Sprint 10 exposed a fundamental architectural insight: the matching engine was conflating **Functional Role Classification** (*"What functional category is this role?"*) with **Evidence Richness** (*"How much information does the job description contain?"*).

By treating these independent variables as a single coupled metric, the system was vulnerable to two systemic failure modes:
1. **The Executive Leak Loophole:** High-seniority irrelevant roles (e.g., CTO, Sales Director) with high evidence richness leaked through deterministic gates and matched downstream keywords (e.g., *CRM*, *Growth*), erroneously climbing to `CONSIDER` or `PURSUE`.
2. **The Sparse-JD Miss Gap:** Highly relevant marketing leadership roles with sparse or truncated description texts were penalised for missing dimensions (`Missing = 0` score). This dragged their final scores down, forcing a `PASS` (rejection) decision.

Historically, the system treated **Missing Evidence as Negative Evidence** (`Missing Evidence ➔ 0 ➔ PASS`). To build a resilient, future-proof, and scale-ready system, we must separate these concepts.

## Decision

We establish a formal architectural boundary separating **Functional Role** from **Evidence Richness**, integrating both as decoupled, orthogonal dimensions within RADAR's evidence-first architecture.

```
                      [ Ingested Opportunity ]
                                 │
                                 ▼
                        [ Normalization Layer ]
                                 │
                                 ▼
                     [ Pluggable Classifier ]
            Orchestrates pluggable evaluation providers:
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
  [ RegexProvider ]      [ OntologyProvider ]     [ LLMProvider ]
         │                       │                       │
         └───────────────────────┼───────────────────────┘
                                 ▼
                      [ ExtractionEvidence ]
                Unified evidence schema for ALL extractors
                                 │
                                 ▼
                      [ Capability Engine ]
             Evaluates continuous fit over dimensions
            Computes Evidence Sufficiency Index (ESI)
                                 │
         ┌───────────────────────┴───────────────────────┐
         ▼                                               ▼
 [ Recommendation Engine ]                     [ Workflow Status Engine ]
  Maps capabilities to:                         Determines evidence state:
   - PURSUE                                      - READY (Proceed to evaluate)
   - CONSIDER                                    - INSUFFICIENT (Needs Better Evidence)
   - PASS                                        - STALE / FAILED / UNKNOWN
```

### 1. Introduce the Unified `ExtractionEvidence` Protocol
To enforce strict decoupling and eliminate custom extractor interfaces, we establish a **Universal Extraction Protocol**. Every extractor (Functional Role, Technology Stack, Reporting Line, Budget, Mandate) must emit evidence using the exact same contract. The Capability Engine consumes this unified shape exclusively, completely decoupled from how or where the evidence was generated:

```typescript
export interface ExtractionEvidence {
  dimension: string;        // e.g., "functionalCategory", "technologyStack"
  value: any;              // e.g., "Marketing Leadership", ["Salesforce", "Marketo"]
  confidence: number;       // Consensus confidence score [0.0 - 1.0]
  provider: string;         // Name of the primary consensus provider (or "Consensus")
  version: string;          // Extractor or prompt version
  timestamp: string;        // Ingestion timestamp
  lifecycle: "ACTIVE" | "SUPERSEDED" | "RETRACTED" | "EXPIRED"; // Governance lifecycle state
  evidence: Array<{
    quote: string;          // Verbatim source snippet
    provenance: string;     // Contextual source tracking
  }>;
  metadata?: {
    providers?: Array<{     // Individual provider confidence scores
      name: string;
      confidence: number;
    }>;
    alternatives?: Array<{  // Alternative classification categories for downstream calibration
      category: string;
      confidence: number;
    }>;
    latencyMs?: number;     // Execution performance metric
    [key: string]: any;
  };
}
```

### 2. Generalise the Orchestration Layer
We reject hardcoding dedicated classifier orchestration. Instead, we establish a generalised, reusable **Classifier** framework (`Classifier.ts`).
* The orchestrator manages executing pluggable **Providers** (`RegexProvider`, `OntologyProvider`, `LLMProvider`, `EmbeddingProvider`).
* No individual provider owns the final answer; they contribute raw inputs to the orchestrator.
* **Consensus Confidence:** The orchestrator evaluates the contributions, resolves a unified category classification, and computes a **Consensus Confidence** score alongside individual **Provider Confidence** records inside the `metadata.providers` array.
* Future classifiers (e.g., `IndustryClassifier`, `CompanyClassifier`) will subclass or reuse this orchestrator without duplicating logic.

### 3. Implement the Evidence Sufficiency Index (ESI)
We reject hardcoded character counts or dimension rules in the core pipeline. Instead, we introduce an **Evidence Sufficiency Index (ESI)** model, which evaluates the structural density of the opportunity:
$$\text{ESI} = 0.40 \cdot \text{Dimension Coverage} + 0.30 \cdot \text{Evidence Completeness} + 0.20 \cdot \text{Text Richness} + 0.10 \cdot \text{Extraction Confidence}$$
* **Evidence Completeness:** Replaces simple reference counts, measuring the richness and validity of structural citations (such as quotes, PDFs, or metadata) rather than just character volume.
* For V1, the ESI encapsulates heuristics internally, allowing us to tune the ESI formula downstream without modifying the pipeline contract.

### 4. Separate Recommendations from Workflow States
We maintain the recommendation decisions as strictly **`PURSUE`**, **`CONSIDER`**, and **`PASS`**. 
* We introduce an independent **Workflow Diligence Status** for the opportunity: **`READY`**, **`INSUFFICIENT`**, **`STALE`**, **`FAILED`**, **`UNKNOWN`**.
* If a job matches our target profile with high confidence (`functionalCategory` is primary) but has low evidence sufficiency (`ESI` is low), its recommendation remains `CONSIDER` or `PURSUE`, but its Diligence Status is set to `INSUFFICIENT`.
* In the UI, these `INSUFFICIENT` jobs are routed to a completely separate queue: **"Needs Better Evidence"**. This queue exposes targeted actions such as:
  1. *Re-scrape job description*
  2. *Open original posting*
  3. *Review manually*
  4. *Mark as ignore*

### 5. Concentric Ring Taxonomy
We split and refine our 15-category functional taxonomy into three concentric rings mapping to our candidate matching policies:
1. **Primary (Target):** `Marketing Leadership`, `Marketing Operations`, `Demand Generation`
2. **Adjacent (Peripheral Alignment):** `Revenue Operations`, `Partnerships`, `Customer Success`, `Enterprise Sales`, `Channel Sales`
3. **Excluded (Out-of-Scope):** `Engineering`, `Product`, `HR`, `Finance`, `General Management`, `Consulting`, `Other`

## Consequences

- **Extreme Architectural Purity:** The LLM is confined to producing structured facts and evidence under a unified platform contract. It never directly executes recommendation logic or acts as an un-auditable gatekeeper.
- **Permanent Architectural Invariant:** Added directly to the RADAR Constitution:
  > *"All extractors emit only ExtractionEvidence. No extractor may communicate directly with the Capability Engine through a custom interface."*
- **Vendor-Agnostic Extensibility:** Providers can be hot-swapped (e.g., migrating from Groq/Llama to a local fine-tuned model) with zero modifications to the capability and recommendation engines.
- **Clean Shortlist Queue:** Shortlists remain highly qualified. Truncated or sparse opportunities are isolated in the "Needs Better Evidence" queue for automated re-scraping or curation.
- **Taxonomy-Driven Analytics:** The multi-class functional taxonomy opens up powerful downstream analytics, including fine-grained heatmaps, trend curves, and targeted career transition mapping.
